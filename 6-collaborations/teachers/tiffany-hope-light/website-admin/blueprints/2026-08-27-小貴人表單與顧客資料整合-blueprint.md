## 1. 這份文件要解決什麼

Tiffany 目前約有 400 位曾在 IG 回覆、表示想購買小貴人的人。因為已經過了幾個月，預計透過專屬登記表提供優惠，並讓有需要的人登記 10 分鐘「創賦密碼靈魂藍圖諮詢」。

這次不能只做一張收件表，還需要回答五件事：

1. 誰已填表、誰尚未處理？
2. 誰是網站舊客、誰是新客？
3. 誰已付款、待出貨、已出貨？
4. 誰想要諮詢、是否已排時間？
5. 誰同意接收未來行銷訊息、誰沒有同意？

本 Blueprint 的目的，是讓 mamasan 先核對一套可執行的資料架構，再決定是否交由 Tiffany 確認。它不是已核准的報價、合約或上線成果。

## 4. 建議的整體架構

**[新設計]**

```text
約 400 位 IG 意願名單
          │
          ▼
HopeBox 小貴人專屬登記表（Elementor）
          │
          ├── 原始送出備份 ──► Elementor Submissions
          │
          └── 自動傳送 ──────► Airtable CRM
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                 ▼
               聯絡／追蹤        Woo 訂單摘要       諮詢任務摘要
                                      │                 │
                                      ▼                 ▼
                            WooCommerce 正式訂單   10 分鐘專用排程
                            付款／地址／出貨主檔    預約時間正式主檔
```

### 4.1 每套系統只負責自己最擅長的事

| 系統 | 在本案的角色 | 正式保存的資料 |
|---|---|---|
| Elementor Submissions | 原始表單收件匣／備份 | 顧客當時實際送出的內容、送出時間、同意版本 |
| Airtable | 營運 CRM／每日工作台 | 一人一筆顧客、活動登記、負責人、下一步、訂單與諮詢摘要 |
| WooCommerce | 商店正式帳本 | 商品、金額、付款、完整收件地址、出貨與退款狀態 |
| HopeLight 預約或獨立短時段排程 | 預約正式帳本 | 諮詢日期、時間、狀態與預約編號 |
| MailPoet（未來） | 經同意後的行銷名單 | 明確同意接收行銷訊息的人，不是所有買家 |

核心原則：**Airtable 是統一看板，不是新的收銀台或出貨系統。**

## 5. Airtable 建議資料表

### 5.1 顧客 Contacts

用途：一個人只建立一筆主要顧客資料。

建議欄位：

- 顧客 ID
- 姓名／希望稱呼
- 手機號碼
- Email
- IG 帳號
- WooCommerce 顧客 ID（沒有帳號可留空）
- 最初來源
- 客戶狀態
- 負責人
- 最近聯絡日
- 下一次聯絡日
- 行銷同意狀態
- 不再聯絡註記
- 建立日／更新日

### 5.2 活動登記 Campaign Registrations

用途：記錄某位顧客參加哪一次活動；同一個人未來可參加不同活動，不必重複建立顧客。

建議欄位：

- 登記 ID
- 對應顧客 ID
- 活動代碼，例如 `小貴人_IG回覆優惠_2026`
- Elementor Submission ID
- 登記時間
- IG 資格核對狀態
- 優惠資格狀態
- 優惠到期日
- 是否需要 10 分鐘諮詢
- 想了解的主題
- 顧客備註
- 個資告知版本
- 必要處理同意時間
- 行銷同意時間（若有）
- 目前處理階段
- 流失／未完成原因

### 5.3 訂單 Orders

用途：保存 WooCommerce 訂單的管理摘要，不複製全部敏感資料。

建議欄位：

- WooCommerce 訂單 ID
- 對應顧客 ID
- 對應活動登記 ID
- 商品 SKU／名稱
- 訂單金額
- 優惠代碼或活動代碼
- 建立時間
- 付款狀態
- 出貨狀態
- 退款／取消狀態
- WooCommerce 後台訂單連結
- 最後同步時間

不建議長期同步到 Airtable：完整宅配地址、超商門市細節、付款憑證、信用卡資訊。

### 5.4 諮詢 Consultations

用途：管理有勾選 10 分鐘諮詢的人。

建議欄位：

- 諮詢 ID
- 對應顧客 ID
- 對應訂單 ID
- 諮詢資格狀態
- 排程狀態
- 預約日期／時間
- 預約系統 ID
- 完成狀態
- 改期次數
- 非醫療性的簡短準備標籤
- 後續行動

### 5.5 任務 Follow-ups

用途：避免 400 筆名單只停在「記得之後聯絡」。

建議欄位：

- 任務 ID
- 對應顧客／登記／訂單
- 任務類型
- 到期日
- 負責人
- 狀態
- 處理結果
- 下一個任務日期

## 6. 小貴人表單欄位調整

**[新設計]**

| 原始欄位 | 建議處理 | 理由 |
|---|---|---|
| 真實姓名／暱稱 | 改為「姓名／希望我們如何稱呼您」 | 避免一個欄位同時要求兩種不同資料 |
| IG 帳號／聯繫電話 | 拆成兩個必填欄位 | IG 用於核對原始名單；電話用於後續聯絡與訂單比對 |
| Email | 登記時可選填，結帳時依 WooCommerce 設定收取 | 避免活動表單過長，同時保留寄送訂單通知的需要 |
| 完整收件資訊 | 從活動表單移除，改在 WooCommerce 結帳時填 | 付款前先不蒐集不必要的完整地址，也避免兩邊資料不一致 |
| 是否需要諮詢 | 保留必填 | 用來建立諮詢任務 |
| 想了解或突破的面向 | 保留選填、可複選 | 用於分流，不要求填寫醫療診斷或詳細健康史 |
| 備註 | 保留選填 | 提供顧客補充，但需限制內部可見範圍 |
| 個資告知與必要處理同意 | 新增必填 | 留下蒐集目的、使用方式與顧客同意的證據 |
| 未來行銷訊息同意 | 新增獨立選填 | 購買或填表不等於同意未來行銷 |

## 7. 既有 WooCommerce 顧客如何進 Airtable

**[新設計]**

### 7.1 第一次匯入

不是只匯入 WooCommerce 的 Customers 畫面，而是同時讀取：

1. WooCommerce 顧客帳號。
2. 歷史訂單。
3. 訪客結帳訂單；這類訂單的 `customer_id` 可能是 `0`，但仍有訂單聯絡資料。

匯入步驟：

1. 先做唯讀盤點，統計顧客帳號、訂單、訪客訂單與欄位完整度。
2. 在本機產生不含敏感值的數量與衝突報告。
3. 標準化 Email、台灣手機號碼與 IG 帳號。
4. 先預覽將新增、更新、需人工確認的筆數。
5. mamasan 核對後才正式寫入 Airtable。
6. 匯入後比對總數、抽樣與重複情況。

本案只處理 HopeBox／希望之光網站的顧客與訂單。先前專案中已隔離的 MEGAWING 舊國外客戶資料，不得因這次整合而自動匯入。

### 7.2 去重規則

依以下順序判斷是否為同一人：

1. 相同 WooCommerce 顧客 ID。
2. 相同且有效的 Email。
3. 相同且已標準化的手機號碼。
4. IG 帳號只作輔助核對，因帳號可能改名。
5. 只有姓名相同時不得自動合併，交由人工確認。

所有自動合併都應保留來源 ID；無法確定時寧可暫時分開，也不要把兩個人的紀錄混在一起。

### 7.3 未來同步

- 新表單：Elementor → Airtable。
- 新訂單與訂單狀態：WooCommerce → Airtable。
- 每日一次：比對 WooCommerce 與 Airtable 是否漏單或狀態不同。
- 初期採單向同步，不允許 Airtable 回寫付款、地址或退款資料到 WooCommerce。
- API 金鑰、Webhook 密鑰及 Airtable Token 只能存放在伺服器或受控的秘密設定，不可放進公開網頁、Markdown、Git 或聊天紀錄。

## 8. 建議的處理狀態

活動登記流程：

```text
新登記
  ↓
待核對 IG 資格
  ├── 不符合／需人工確認
  └── 符合
        ↓
      待付款
        ├── 未付款到期
        ├── 取消
        └── 已付款
              ↓
           待出貨 → 已出貨
              ↓
      有選諮詢？──否──► 結案
          │
          是
          ↓
      諮詢待排 → 已預約 → 已完成 → 結案
```

訂單狀態仍以 WooCommerce 為準，不應用 Airtable 的文字覆蓋 WooCommerce 正式狀態。

## 9. 個資與權限界線

**[新設計／待 mamasan 核對]**

1. Airtable 是外部雲端服務；採用前需確認帳號由誰持有、誰付費、誰可匯出及離職／終止合作時如何移交。
2. Tiffany 可只使用簡化後的 Airtable Interface，不必看到完整底層資料表；是否開放及開放範圍由 mamasan 決定。
3. 只讓需要處理訂單或顧客的人看到資料，取消不再需要者的權限。
4. Airtable 不保存完整收件地址；需要出貨時回 WooCommerce 查看。
5. 「身體健康／能量調整」只存一般分流標籤，不在 CRM 自行記錄診斷、用藥、病史或推測。
6. 既有買家不得自動標記為同意行銷；沒有證據時填「未知／未取得」。
7. 表單需附個資告知，說明蒐集者、目的、資料類別、利用期間／地區／對象／方式、當事人權利，以及不提供資料的影響。
8. 客戶資料、匯出 CSV、API 回應、Token、Cookie 與偵錯檔不得提交到 Git。
9. 尚需由 mamasan 決定未成交名單保留多久，以及顧客提出查詢、更正、停用或刪除要求時由誰處理。

## 11. 建議上線階段

### Phase 0：決策與資料界線

- mamasan 核對本 Blueprint。
- Tiffany 核准品項、價格、庫存、優惠與諮詢規則。
- 決定 Airtable 是否可作為外部 CRM，以及帳號與權限歸屬。
- 核准個資告知與行銷同意文字。

完成條件：第 10 節沒有會阻擋上線的空白決策。

### Phase 1：用假資料建立 Airtable

- 建立五張資料表與簡化工作介面。
- 使用假姓名、假電話、假訂單進行測試。
- 建立新名單、待付款、已付款、待出貨、諮詢待排等檢視。

完成條件：尚未使用真實個資，也能完整跑完一筆流程。

### Phase 2：建立活動表單與結帳流程

- 建立 Elementor 表單與成功頁。
- 建立 Elementor Submissions 保存及通知。
- 建立安全的 Airtable 傳送流程。
- 建立正確 SKU、活動價格／一次性優惠機制與 WooCommerce 結帳。
- 使用測試訂單驗證付款、取消與出貨狀態。

完成條件：假資料從填表到訂單、諮詢任務都只建立一次。

### Phase 3：既有 WooCommerce 資料匯入

- 先做唯讀盤點及去重預覽。
- mamasan 核對新增、合併與衝突數量。
- 正式匯入顧客與歷史訂單摘要。
- 抽查訪客訂單與已註冊顧客。

完成條件：WooCommerce 正式資料未被修改，Airtable 沒有明顯重複或錯誤合併。

### Phase 4：小量試跑後再發給約 400 人

- 先用內部 3–5 筆測試。
- 再選少量真實名單試跑聯絡、付款與排程。
- 確認人力與錯誤處理後，才發送給全部名單。

完成條件：沒有漏件、重複顧客、錯誤價格、錯誤庫存或無法承接的預約。

## 12. 驗收標準

正式上線前至少通過以下測試：

- 同一人重複填表時，不會自動建立兩個顧客。
- 舊 WooCommerce 顧客填表後，能連到原顧客，而不是再建一筆。
- 沒有會員帳號的訪客訂單也能被辨識。
- 表單、訂單與諮詢各自有唯一 ID，可以互相追查。
- WooCommerce 訂單變成已付款、取消或退款後，Airtable 摘要會更新。
- 完整收件地址沒有被不必要地複製到 Airtable。
- 沒有行銷同意的人不會進入行銷名單。
- 同步失敗時會留下可處理的錯誤，而不是安靜漏單。
- 測試紀錄、匯入報告與 Git 中不含真實個資或秘密金鑰。
- mamasan 能從簡化畫面看見「今天要處理誰、下一步是什麼」。
