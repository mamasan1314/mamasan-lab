## 1. 結論

本案可以在現有 HopeBox 架構上完成，不需要另建 CRM 或自行開發金流。推薦的 MVP 是：

```text
廣告／IG／直接網址
          ↓ source code / UTM
        蠟燭 LP
          ├── 直接訂購 → 十款數量合計 21 → WooCommerce 結帳
          └── 先諮詢   → LINE「蠟燭」→ 人工排 10 分鐘 → 回 WooCommerce 結帳
                                                   ↓
                                          WooCommerce 訂單
                                                   ↓ 唯讀
                                            Hope Light CRM
```

這個設計讓 WooCommerce 保持唯一交易主檔，LINE 只負責關係與諮詢，CRM 只負責看見工作。

**本案的成敗指標不只是「能不能結帳」，而是「Tiffany 之後能不能不找我們就自己改」。**
售價、庫存組數、含運、贈品與十款款名都是會變的營運參數。只要它們留在寫死的 HTML 裡，
每次調整都得走一次 Darren → AI → 重新發布的來回；一旦做成後台欄位，這些來回就消失了。
所以「自助維護」在本案是架構需求，不是加分項，驗收條件第 10.1 節排在最前面。

## 2. Tiffany 的自助維護範圍

原則：**每一個會變的營運數字，只有一個地方可以改；其他所有頁面都去讀它，不得抄寫。**

### 2.1 她可以自己改（不需要工程協助）

| 值 | 她在哪裡改 | 哪些地方跟著變 |
|---|---|---|
| 21 顆組售價 | Woo 商品 → 一般 → 售價 | Woo 商品頁、購物車、結帳、Email、LP 價格區與方案比較表 |
| 單顆售價 | 單顆蠟燭商品 → 售價 | LP 方案比較表；限定組差額自動重算，不寫死「61 元」 |
| 首批組數／是否售罄 | Woo 商品 → 庫存 | 商品頁可否下單、LP 限量文案與 CTA 狀態 |
| 實際運費規則 | Woo → 運送設定 | 結帳時計算出的運費 |
| 「全台含運」這句**承諾** | 外掛設定頁 →「組合內容」 | LP 含運標示、Woo 商品頁說明 |
| 玻璃燭台是否附贈與剩餘數量 | Woo 燭台商品 → 庫存 | LP 內容物清單、Woo 商品頁說明；贈完自動停止承諾 |
| 其他組合內容項目 | 外掛設定頁 →「組合內容」 | LP 內容物清單、Woo 商品頁說明 |
| 十款顯示名稱與一句話描述 | 外掛設定頁 →「十款」 | LP 選款區、Woo 選款 UI、購物車、結帳、Email |
| 10 分鐘諮詢說明、次數與使用期限 | 外掛設定頁 →「諮詢」 | LP、Woo 商品頁、訂單 Email |
| LINE「蠟燭」自動回覆文案 | LINE OA Manager | LINE 對話 |

改動即時生效（見 2.4 快取）；且**只影響新訂單**——既有訂單保留下單當下的完整優惠快照，
款名、燭台、諮詢條件與含運承諾都不會被後台改動追溯改寫（見第 6 節）。

### 2.2 「全台含運」不能從運送設定推導

LP 在訪客還沒有地址時就要顯示「全台含運」，但 WooCommerce 的實際運費取決於運送區域、
是否離島、購物車裡有沒有其他商品與選了哪個運送方式。**單一短碼無法安全地反推出這句話**。

所以拆成兩件事：**承諾**是外掛設定頁的一個明確欄位（LP 顯示它），**實際運費**由 Woo
運送設定計算。兩者必須一致，並在部署計畫 Phase 3 逐一實測；不一致時以 Woo 為準，
外掛在後台告警，不得讓 LP 繼續掛著做不到的承諾。

需要在建立運送設定前決定：**離島是否含運**、以及**限定組與其他商品一起買時是整張訂單
免運還是只免限定組**。這兩題見 DECISION-REGISTER 的 `C21-Q11`／`C21-Q12`。

### 2.3 玻璃燭台是有庫存的實體，不是一行可開關的文字

`product-facts.md` 指出整個 repo 只有 LP 文案提過玻璃燭台，數量是否夠賣沒有人確認過。
若它只是設定頁裡的一段文字，系統會在燭台實際用完之後**繼續承諾附贈**。

因此燭台建成**有 SKU 與庫存的 Woo 商品**（隱藏或 bundle component），由限定組成立時扣減。
庫存歸零時，LP 與商品頁自動停止顯示這項贈品，不需要任何人記得去關掉文案。這也讓
Tiffany 管燭台的地方跟她管組數的地方是同一個 Woo 庫存欄位，不必多學一套。

### 2.4 改完之後真的要看得到：快取

「改完即時同步」是一句會被快取打破的承諾。WordPress 頁面快取、Jetpack、CDN 與主機層
快取都可能讓 LP 繼續顯示舊價格，而後台看起來明明已經改好了。

因此：設定或商品儲存後**自動 purge 相關頁面快取**（LP、商品頁、任何嵌了短碼的頁面）；
驗收一律用**未登入的瀏覽器或無痕視窗**確認，不接受管理員視角看到新值就算通過
（管理員常繞過快取）。做不到自動 purge 時，設定頁必須明確告訴她還要按哪裡。

### 2.5 需要工程協助（刻意不開放）

十款的 ASCII key、合計必須為 21 的驗證規則、order item meta 與快照結構、付款 gateway、
CRM 欄位與 feature flag 的程式行為。這些改錯會讓既有訂單讀不懂或結帳壞掉，
不適合放進後台自助欄位。

### 2.6 這對 LP 的直接影響

LP 目前是靜態 HTML（Artifact），價格與贈品寫死在頁面上共八處。要達成 2.1 與 2.4，
**LP 必須進 WordPress 成為子佈景主題頁面範本**（D-001 實作方式第 1 順位），
所有商業數字改用外掛提供的短碼輸出。若 LP 停在靜態 HTML，2.1 表格的前四列就不成立，
每次改價都要回到人工改 HTML 並重新發布。

## 5. 顧客旅程

### 5.1 直接訂購

1. 顧客由 LP 點「直接訂購」。
2. WooCommerce 商品頁顯示十款非負整數數量欄位與即時合計。
3. 合計不是 21 時不可加入購物車；伺服器端再次驗證，避免繞過前端。
4. 購物車與結帳摘要顯示十款配置、售價、含運與贈品內容。
5. 完成訂單後，配置固化到 order item meta，CRM 可唯讀顯示。

### 5.2 先諮詢

1. 顧客由 LP 點「先做 10 分鐘諮詢」，前往 LINE 並看到明確提示「請傳蠟燭」。
2. LINE「蠟燭」自動回覆提供兩個選項：直接訂購／先排諮詢。
3. 首版由小幫手人工安排 10 分鐘，不啟用 Messaging API 或 LIFF。
4. 諮詢完成後，小幫手傳回帶 `source=line_consult` 的 WooCommerce 商品連結。
5. 顧客自行填滿 21 顆後結帳；不建立選款未完成的半成品訂單。

## 6. 十款配置資料契約

使用穩定 ASCII key，**顯示名稱由後台設定，Tiffany 可隨時改而不破壞既有訂單**：

| key | 出廠預設顯示名稱 |
|---|---|
| `peaceful-night` | 安然入夜 |
| `good-luck` | 好運爆棚 |
| `boundaries` | 小人退散 |
| `abundance` | 財富豐盛 |
| `customers` | 吸引顧客 |
| `romance` | 吸引桃花 |
| `study-career-growth` | 學/事業進步 |
| `benefactors` | 貴人常臨 |
| `relationship-warmth` | 感情升溫 |
| `cleansing` | 淨化除穢 |

每個值必須是 `0..21` 的整數，十欄合計必須等於 `21`。Order item 保存 key、下單當下的
顯示名稱、數量與 schema version，所以後台改名之後回頭看舊訂單仍讀得懂。

建議 meta，**注意層級不同**：

| meta key | 層級 | 值 |
|---|---|---|
| `_hopelight_c21_schema_version` | order **item** meta | `1` |
| `_hopelight_c21_mix` | order **item** meta | 十款 key／quantity／下單當下顯示名稱的 JSON；只在伺服器端產生 |
| `_hopelight_c21_offer` | order **item** meta | **優惠快照**，見下方 6.1 |
| `_hopelight_c21_traffic_source` | order meta | allowlist 入口來源，例如 `lp_direct`、`line_consult`、`unknown` |
| `_hopelight_c21_journey_path` | order meta | `direct` 或 `via_consult_link` |
| `_hopelight_c21_consultation_status` | order meta | `not_scheduled`／`scheduled`／`completed`；MVP 見 6.2 |

配置與優惠屬於那一列商品，必須走 `woocommerce_checkout_create_order_line_item` 寫成
item meta，才會出現在購物車、結帳、Email 與後台訂單的該列；來源與旅程路徑描述的是整張
訂單，放 order meta。兩者不可互換。

### 6.1 優惠快照：後台改設定不得追溯改寫舊訂單

只快照款名並不夠。Tiffany 今天關掉玻璃燭台、把諮詢期限從 30 天改成 14 天，或改掉含運
承諾，**昨天已經成立的訂單權益不能跟著變**。設定只影響新訂單，這是不可退讓的規則。

因此下單當下必須把整份對外承諾固化進 `_hopelight_c21_offer`：

| 欄位 | 內容 |
|---|---|
| `offer_version` | 組合內容的版本序號，後台每次存檔遞增 |
| `bundle_items` | 當時的組合內容清單（含**是否附玻璃燭台**） |
| `shipping_promise` | 當時對外的含運承諾文字與範圍 |
| `consultation` | 當時的諮詢分鐘數、次數與到期日（到期日以下單日推算後固化，不存「30 天」這種相對值） |
| `display_names` | 當時使用的十款顯示名稱 |
| `captured_at` | 固化時間 |

購物車、結帳、Email、後台訂單與 CRM 一律顯示快照值，不重新查後台設定。客服要回答
「這張訂單到底附不附燭台」時，答案只看快照。

### 6.2 來源不等於諮詢真的發生

`traffic_source=line_consult` 只證明顧客點了那條連結，**不證明諮詢確實完成**。把「來源」
與「諮詢狀態」混成同一個欄位，會讓 CRM 顯示出沒有根據的「已諮詢」。

所以拆成三個獨立欄位：`traffic_source`（從哪裡來）、`journey_path`（走哪條路徑進來）、
`consultation_status`（諮詢到什麼程度）。前兩者可由連結自動判定；**第三者只能由人工
更新**。

MVP 不做諮詢狀態管理，因此 `consultation_status` 一律寫 `not_scheduled`，**CRM 不得
顯示成「已諮詢」**，最多顯示「由諮詢連結進入」。要顯示真實諮詢狀態，得等到有人負責
維護它的那一版。

**顯示注意**：底線開頭的 meta 在 WooCommerce 屬 hidden meta，預設不會顯示在前述五個
位置。顯示層需另外走 `woocommerce_order_item_display_meta_key`／`woocommerce_display_item_meta`
過濾器，或另存一份不帶底線的人類可讀欄位。這是驗收條件 10.3.1 的前提，不是實作細節。

**與既有歸因的分工**：已有 2026-09-04〈訂單來源歸因〉Blueprint 在追 WooCommerce 內建的
`_wc_order_attribution_*`。若內建可用，它負責通用行銷來源（referrer、utm、裝置）；
`_hopelight_c21_traffic_source` 只負責本案 allowlist 語意（`lp_direct`／`line_consult`）。
兩者並存、互不覆蓋、互不推導。

不要保存 LINE 對話、自由文字診斷、靈魂藍圖內容或 LINE user ID。

## 7. 元件邊界

### 7.1 LP

- 位置：WordPress 子佈景主題頁面範本，不是靜態 Artifact（見 2.6）。
- 售價、單顆價、差額、庫存／售罄、含運承諾、贈品與十款款名一律以短碼輸出，
  頁面不寫死數字；含運顯示的是**承諾欄位**，不是從運送設定推導（見 2.2）。
- 顯示產品內容與兩個 CTA。
- 透過固定 allowlist 參數傳遞來源，不直接寫訂單或顧客資料。
- JavaScript 失效時仍能到達 WooCommerce 商品頁與 LINE。

### 7.2 `hopelight-candle21-commerce` 外掛

- 只對指定 WooCommerce product ID／SKU 啟用十款選擇 UI。
- 提供 wp-admin 設定頁：組合內容、十款顯示名稱與描述、諮詢說明、feature flag；
  權限沿用 `manage_woocommerce`，欄位需有中文說明與即時驗證。
- 提供短碼給 LP 讀取售價、單顆價、差額、庫存狀態、含運、贈品與十款款名。
- 驗證 cart、checkout 與 order item meta。
- 顯示於購物車、結帳、顧客 Email 與後台訂單（含前述 hidden meta 的顯示處理）。
- 提供 feature flag／kill switch；關閉後不影響其他商品結帳。
- 不處理信用卡、不自行建立訂單表、不保存秘密、不複製一份售價或庫存。

### 7.3 CRM 看板

- 延續 `manage_woocommerce` 權限與唯讀原則。
- 顯示配置摘要、優惠快照、traffic source 與 journey path；必要時連回 Woo 訂單。
- **不得把 journey path 顯示成「已諮詢」**；MVP 的 `consultation_status` 恆為
  `not_scheduled`，最多顯示「由諮詢連結進入」（見 6.2）。
- 顯示名稱與優惠一律取自訂單快照，不查現行後台設定。
- 不在 CRM 內修改付款、配置、地址或訂單狀態。

### 7.4 LINE

- 使用 OA Manager 設定關鍵字與核准文案。
- 首版不使用 Messaging API、Webhook、LIFF 或外部 LINE user profile。
- 所有連結只帶非個資 source code。

## 8. 失敗與降級

| 情境 | 行為 |
|---|---|
| JavaScript 未載入 | Woo 商品頁仍顯示欄位；伺服器端拒絕非 21 的配置 |
| 顧客繞過前端送出 | `add_to_cart_validation`／checkout validation 拒絕並顯示原因 |
| 商品售罄 | WooCommerce 庫存阻擋下單；LP 短碼自動顯示售罄，不需人工改文案 |
| 燭台庫存歸零 | LP 與商品頁停止顯示該項贈品；限定組仍可販售，已成立訂單依快照照常出貨 |
| 後台設定留白或填錯 | 設定頁擋下並提示，不存檔；前台依下方「降級方向」處理 |
| 短碼失效 | LP 顯示保守的靜態備援文字並連向 Woo 商品頁，不顯示錯誤碼 |
| 快取沒清掉 | 儲存後自動 purge；purge 失敗時後台顯著告警並告知手動清除位置 |
| LINE 自動回應失效 | LP 的直接購買仍可用；公開頁不得承諾即時自動回覆 |
| CRM 擴充失效 | 不阻擋 WooCommerce 結帳；回 Woo 訂單頁工作 |
| 外掛需緊急停用 | feature flag 優先；必要時後台停用，LP 暫時只留 LINE |

**降級方向：承諾要 fail closed，不要 fail open。** 設定遺失或讀取失敗時，**絕對不可以
自動退回「附燭台」「全台含運」這類促銷承諾的出廠預設**——那等於在沒有人決定的情況下
對顧客做出成本承諾。正確方向是：

| 壞掉的東西 | 降級行為 |
|---|---|
| 選購功能異常 | 關閉限定組結帳，顯示聯絡方式，不讓半殘的流程收錢 |
| 贈品或含運設定異常 | **隱藏**該項承諾，後台顯著告警，不顯示未確認的贈品 |
| 售價讀取異常 | 不顯示價格、不可下單；售價只從 WooCommerce 商品取得，**不用外掛預設值猜** |
| 十款顯示名稱遺失 | 可退回出廠款名（這不是商業承諾，只是標籤） |

## 9. 安全與個資

- WooCommerce 既有結帳頁負責姓名、電話、Email 與地址；LP、LINE URL 與 Git 不帶個資。
- 前端傳來的價格、總數、source 與顯示名稱一律不可信；伺服器以 allowlist 重算。
- 後台設定頁的所有欄位需 escaping 與型別驗證；顯示名稱輸出一律 escape，不接受 HTML。
- 所有管理功能使用 WordPress capability 與 nonce。
- Log、部署收據與測試 fixture 只保存訂單假 ID／遮蔽摘要，不保存真實顧客資料。
- Secret、Cookie、Token、匯出 CSV 與聊天內容維持 Git ignore／本機或網站內保存。

## 10. 驗收條件

### 10.1 Tiffany 的後台自助 UI（本案最高優先）

1. Tiffany 只用 wp-admin、不需要任何工程協助，就能改：21 顆組售價、單顆售價、
   庫存組數、是否含運、組合內容（含玻璃燭台）、十款顯示名稱與描述、諮詢說明。
2. 上述任一項改完後，**LP、Woo 商品頁、購物車、結帳與訂單 Email 同時跟著變**，
   沒有任何一處需要另外改 HTML 或重新發布頁面。
3. **同步要在未登入的瀏覽器成立**：以無痕視窗驗收，不接受只有管理員視角看得到新值
   （管理員常繞過快取）。儲存後相關頁面快取自動 purge。
4. 十款設定是一頁十列：key 唯讀且不需要她理解，顯示名稱與描述可直接編輯。
5. 庫存為 0 時，LP 與商品頁自動呈現售罄狀態；燭台庫存為 0 時自動停止顯示該項贈品，
   兩者都不需要她手動改任何文案。
6. 欄位留白或填錯（負數、非數字、超長字串）時，畫面即時給中文提示並拒絕存檔，
   不會讓前台出現空白、錯誤碼或壞掉的版面。
7. **改設定不得影響已成立訂單**：改完之後回頭看先前的測試訂單，款名、燭台、含運承諾與
   諮詢到期日必須與下單當時完全一致。
8. **實測方式**：由 mamasan 模擬 Tiffany，在無人指導、不看文件的情況下完成三件事
   ——改一次組售價、改一次庫存組數、關掉玻璃燭台這項贈品——並以無痕視窗確認前台全數
   同步，再確認舊訂單沒有被改動。任何一件需要開口問，就算這一節不通過。

### 10.2 顧客端選款 UI

1. 十款數量欄位、即時合計，以及「還差幾顆／已超過幾顆」的中文提示。
2. 合計不是 21 時，加入購物車按鈕停用並說明原因，不是按下去才報錯。
3. iOS Safari、Android Chrome 與 LINE 內建瀏覽器皆可操作；數字欄位不觸發縮放。
4. JavaScript 失效時欄位仍可送出，由伺服器擋下並顯示原因。
5. 20、22、負數、小數、缺欄、未知 key 與竄改 payload 一律被伺服器拒絕。

### 10.3 資料一致性與不回歸

1. 購物車、結帳、訂單信件、後台訂單與 CRM 顯示同一份配置與同一份優惠快照。
2. **快照不可變測試**：建立訂單 → 改後台（關燭台、改諮詢期限、改款名、改含運承諾）
   → 該訂單在五個位置顯示的內容完全沒變；同時新建的訂單反映新設定。
3. 來源只接受 allowlist；未知值歸為 `unknown`，不原樣輸出。
4. CRM 對 `journey_path=via_consult_link` 的訂單**不顯示為「已諮詢」**。
5. LP 顯示的含運承諾與結帳實際算出的運費一致（含離島情境與混合購物車情境）。
6. 一筆直接購買與一筆 LINE 諮詢後購買都能完成端對端測試。
7. 其他既有商品的加入購物車、付款與訂單流程不受影響。
8. 關閉 feature flag 後，蠟燭自訂欄位停止作用，網站與其他 Woo 商品仍正常。
9. LINE「蠟燭」、歡迎訊息、LP、Woo 商品與 CRM 的名稱、價格及連結一致——
   在 10.1.2 成立的前提下，這一項應自動成立，不再靠人工比對。

## 11. 尚待決定與不包含

售價、含運與贈品**不擋開發，也不擋草稿商品測試**。以目前 LP 的值（NT$2,980、全台含運、
玻璃燭台 1 個）出廠，並依第 2 節全部做成 Tiffany 可自助修改的欄位；她要調整時自己改，
不需要回頭找我們。

但**「欄位可以改」解決的是維護成本，不等於她已經接受這個商業承諾**。售價、含運與燭台
是這張頁面上唯一會產生每筆訂單實際成本的東西，寫上去就退不掉。所以正式公開前保留一道
閘門，形式是**看畫面，不是回答問題**：

- 不擋 Phase 1～4 的開發、草稿商品與未公開測試。
- **公開前**（Phase 5），把做好的 LP 與商品頁實際畫面給 Tiffany 看一次，
  確認上面顯示的售價、含運、燭台與諮詢條件就是她要對外承諾的內容。
- 這是一次確認，不是逐題問卷。她點頭就公開，她要改就自己改欄位——兩條路都不需要
  我們來回。

供她判斷用的一次性資訊：21 × 139 = 2,919，限定組 2,980，差額 61 元要涵蓋運費、燭台與
10 分鐘諮詢，`product-facts.md` 的〈21 顆組〉一節有完整成本推算。

其餘施工閘門見專案 [`DECISION-REGISTER.md`](../projects/2026-09-candle21-commerce/DECISION-REGISTER.md)。
